# Структура проекта

Этот файл объясняет, как устроено приложение и где искать код. Рассчитан на то, что раньше вы писали на Python/Flask и видите Electron/React впервые — поэтому там, где уместно, добавлены аналогии с Flask.

## Три процесса вместо одного

В Flask всё происходит в одном процессе: пришёл HTTP-запрос → выполнился Python-код → отрендерился HTML → ушёл ответ.

Electron-приложение — это **несколько отдельных процессов**, которые общаются между собой не по HTTP, а через внутренний механизм IPC:

```
┌────────────────────────┐          ┌───────────────────────────┐
│      Main process        │   IPC    │      Renderer process        │
│      (Node.js)            │◄────────►│      (окно, Chromium)         │
│                           │  через   │                              │
│      src/main/            │ preload  │      src/renderer/src/         │
│                           │          │      (здесь живёт React)       │
└────────────────────────┘          └───────────────────────────┘
                                              ▲
                                              │ мост между процессами
                                     src/preload/
```

- **Main process** — Node.js-код с полным доступом к файловой системе, сети, ОС. Ближе всего к вашему привычному Flask backend: здесь в будущем будет подниматься HTTP/WebSocket сервер для приёма данных CS2 (Game State Integration), читаться/писаться файлы настроек и т.д. Именно этот процесс создаёт окно приложения.
- **Renderer process** — то, что реально отрисовывается в окне: обычная веб-страница (HTML/CSS/JS), выполняется в Chromium. По соображениям безопасности у неё **нет** прямого доступа к файлам и ОС — как у обычной страницы в браузере. Здесь живёт React-интерфейс.
- **Preload** — небольшой скрипт-мост между ними. Renderer не может напрямую попросить main прочитать файл с диска — вместо этого он идёт через контролируемый API, который preload выставляет наружу (`contextBridge`). Смысловой аналог — как ваш JS на странице делает `fetch('/api/...')` к Flask-роуту, только вместо HTTP здесь `ipcRenderer` ↔ `ipcMain`.

## Как переключаются разделы (React vs Jinja2)

В Flask у вас было бы что-то вроде:

```python
@app.route('/huds')
def huds():
    return render_template('huds.html')

@app.route('/players')
def players():
    return render_template('players.html')
```

Каждый переход — это новый HTTP-запрос, сервер заново рендерит HTML, браузер перезагружает страницу.

В React ([App.tsx](./src/renderer/src/App.tsx)) это выглядит похоже по смыслу, но происходит **целиком в браузере, без запросов к серверу**:

```tsx
<Routes>
  <Route path="/huds" element={<HudsPage />} />
  <Route path="/players" element={<PlayersPage />} />
  {/* ... */}
</Routes>
```

`react-router-dom` слушает изменение URL (в Electron используется `HashRouter`, то есть адрес выглядит как `#/players`) и просто подменяет, какой React-компонент показан — страница не перезагружается, меняется только контент справа. Пункты меню в [Sidebar.tsx](./src/renderer/src/components/Sidebar.tsx) берутся из общего списка [nav.ts](./src/renderer/src/nav.ts), поэтому добавить новый раздел — значит:

1. Создать компонент страницы в `pages/`.
2. Добавить пункт в `nav.ts`.
3. Добавить `<Route>` в `App.tsx`.

## Компонент — это не шаблон, а функция с состоянием

Jinja2-шаблон подставляет переменные один раз при рендере. React-компонент — это JS/TS-функция, возвращающая разметку, которая **может сама себя перерисовывать**, когда меняются данные (`useState`, входные пропсы и т.д.). Пример — [Sidebar.tsx](./src/renderer/src/components/Sidebar.tsx): при клике по пункту меню `NavLink` сам определяет, активен ли он сейчас (`isActive`), и подсвечивает себя — никакого сервера для этого не нужно.

## Куда пойдёт бизнес-логика дальше

Когда будем добавлять реальные данные:

- **Приём данных от CS2 (Game State Integration)** — HTTP-сервер (например, на `express`, концептуально аналог Flask) поднимается в `src/main/`, потому что только у main-процесса есть доступ к сети/файлам. Дальше данные прокидываются в renderer через `preload` + IPC-события в реальном времени.
- **Хранение HUD-тем / игроков / команд / матчей** — чтение и запись файлов (JSON или SQLite) тоже будет жить в `src/main/`, а React-страницы будут запрашивать эти данные через `preload`-мост, а не напрямую.
- **Сами HUD-оверлеи для OBS** — это будет отдельная простая HTML/CSS/JS страница (не часть этого Electron-приложения), которую MPView будет либо генерировать на диск, либо раздавать локальным веб-сервером, чтобы её можно было добавить в OBS как Browser Source.
